# JUC简介

是`java.util.concurrent` 简称, 处理线程的工具包

## 进程和线程

**进程**: 是系统进行资源分配和调度的基本单位, 是线程的容器, 线程的实体, 操作系统结构的基础

**线程**（thread）: 是操作系统能够进行运算调度的最小单位。它被包含在进程之中，是进程中的实际运作单位。一条线程指的是进程中一个单一顺序的控制流，一个进程中可以并发多个线程，每条线程并行执行不同的任务。

## 线程基本状态

1. **新建状态（New）**

   线程对象刚被创建出来，还未调用`start()`方法，仅仅具备了线程本体，操作系统还未为其分配资源、还没开始运行。

   

2. **就绪状态（Runnable）**

   调用`start()`后，线程进入**可运行队列**，已经拿到了除 CPU 时间片之外的所有资源，时刻等待操作系统调度器分配 CPU 执行时间，随时可以运行。

   

3. **运行状态（Running）**

   CPU 正式调度该线程，线程拿到时间片、正在执行自身的代码逻辑。

   时间片耗尽、或被更高优先级线程抢占后，会从运行态回到就绪态。

   

4. **阻塞 / 等待状态（Blocked/Waiting）**

   线程暂停执行、主动 / 被动让出 CPU，暂时不参与调度，分为三类：

   

- **阻塞（Blocked）**：等待获取锁资源（如`synchronized`），拿到锁就回到就绪态
- **无限等待（Waiting）**：主动等待被其他线程唤醒（如`wait()`、`join()`）
- **计时等待（Timed Waiting）**：限时等待，超时或被唤醒就回到就绪态（如`sleep()`、带超时的`wait()`）

1. **终止状态（Terminated/Dead）**

   

   线程代码执行完毕、或被异常终止，线程生命周期彻底结束，永久消亡，无法再恢复运行。

------

### 线程状态流转关系

```
新建 → 就绪 → 运行 ↔ 阻塞/等待 → 就绪 → 运行 → 终止
```

## wait/sleep 的区别

* sleep 是 Thread 的静态方法，wait 是 Object 的方法，任何对象实例都能调用。

* sleep 不会释放锁，它也不需要占用锁。wait 会释放锁，但调用它的前提是当前线程占有锁 (即代码要在 synchronized 中)。

* 它们都可以被 interrupted 方法中断。

## 模式

### 串行模式

一次只能取得一个任务，并执行这个任务

### 并行模式

一个进程里开多个线程，多核 CPU 分别调度，不同线程**在同一时间点同时执行不同任务**

###  并发（Concurrent）

(春运抢票) 指在**同一时间段内**，多个任务**交替执行**，宏观上看似同时进行，微观上是**快速切换**（单核 CPU）

### 并行（Parallel）

(泡方便面) 指在**同一时刻**，多个任务**真正同时**执行，必须依赖**多核 CPU**等硬件支持

### 管程

**解决线程互斥、线程同步**的高级同步机制，简单说就是一个**封装好的、自带锁 + 等待队列的 “安全房间”**,保证同一时间最多只有 1 个线程能进入管程执行

### 用户线程和守护线程

**用户线程**: 自定义线程, JVM 会等所有用户线程都结束，才会退出

**守护线程**: 是**后台服务线程**，默默为用户线程服务(GC垃圾回收), 当所有用户线程都结束时，守护线程会被 JVM 强制杀死



# Lock 接口

## Synchronized 关键字回顾

`synchronized` 是 Java 中的关键字，属于**内置同步锁**，用来解决多线程的资源竞争、保证线程安全。

### 四种修饰用法

1. **修饰代码块（同步语句块）**

- 锁定范围：仅大括号 `{}` 包裹的一段代码
- 锁定对象：调用该代码块的**当前实例对象**
- 粒度更灵活，性能损耗更小

1. **修饰普通成员方法（同步方法）**

- 锁定范围：整个方法的全部代码
- 锁定对象：调用这个方法的**当前实例对象**
- 等价于 `synchronized(this)` 修饰整个方法体

> 🔴 重要继承特性
>
> `synchronized` 不属于方法签名的一部分，**不能被子类继承**：

- 父类方法加了 `synchronized`，子类重写该方法时，默认不会自带同步效果
- 子类重写后，必须**显式重新加上 `synchronized`** 才是同步方法
- 替代方案：子类重写方法内部，主动调用父类的同步方法，间接实现同步

1. **修饰静态方法**

- 锁定范围：整个静态方法
- 锁定对象：**类本身的 Class 对象**，作用于这个类的**全部所有实例对象**
- 所有该类的对象，共用同一把静态锁，不同实例调用都会互斥阻塞

1. **修饰类（锁类对象）**

- 写法：`synchronized(类名.class)`
- 锁定范围：括号内包裹的代码片段
- 锁定对象：该类的 Class 对象，效果和修饰静态方法一致，全局所有对象共用一把锁

## Lock

Lock 锁实现提供了比同步方法、同步语句**更广泛的锁操作**

| 对比维度   | Lock                                                         | synchronized                                                 |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 本质属性   | **是一个类**，是 Java 提供的 API 层面的锁                    | **Java 语言内置关键字**，是语言层面的内置特性                |
| 锁释放方式 | **必须手动释放锁**，需调用`unlock()`方法；若未主动释放，可能引发死锁 | **自动释放锁**，同步方法 / 代码块执行完毕后，系统自动释放锁资源 |
| 使用形式   | 需通过类实现同步访问，需手动控制加锁、解锁流程               | 语法简洁，直接通过关键字修饰方法 / 代码块即可使用            |

![image-20260420161614382](C:\Users\Liyal\AppData\Roaming\Typora\typora-user-images\image-20260420161614382.png)

| 特性     | synchronized（内置锁）                          | Lock（接口实现锁）                          |
| -------- | ----------------------------------------------- | ------------------------------------------- |
| 出身     | Java**关键字**，JVM 原生底层实现                | 普通**接口 + 类实现**，JDK 代码层面实现     |
| 加解锁   | 自动加锁、**自动释放锁**，出代码块 / 方法就解锁 | 必须手动 `lock()` 加锁、`unlock()` 手动解锁 |
| 死锁风险 | 几乎不会，异常也会自动释放                      | 忘记`unlock()`、异常没处理 → **大概率死锁** |
| 锁等待   | 阻塞等待，不能中断、不能超时                    | 可中断等待、限时等待、尝试拿锁              |
| 条件队列 | 只能绑定 1 个 `wait/notify`                     | 可绑定**多个 Condition 条件**               |
| 锁类型   | 非公平锁，不可手动设置                          | 可公平锁 / 非公平锁自由选择                 |

## 虚假唤醒问题

**线程在调用 `wait()`、`await()` 等方法进入等待状态后，没有收到明确的 `notify()` 或 `signal()` 调用，却“莫名其妙”地苏醒过来**

哪里沉睡就哪里醒的问题: 

![image-20260420163649107](C:\Users\Liyal\AppData\Roaming\Typora\typora-user-images\image-20260420163649107.png)

**正确的处理方式：循环检查**

**始终使用 `while` 循环来包围 `wait()` / `await()`**，这样每次被唤醒（无论是正常还是虚假）都会重新检查条件，不满足则继续等待

```java
// 创建Lock
private Lock lock = new ReentrantLock();
private Condition condition = lock.newCondition();

// +1
public void incr() {
    // 上锁
    lock.lock();
    try {
        // 判断
        while (number != 0) {
            condition.await();
        }
        // 干活
        number++;
        System.out.println(Thread.currentThread().getName()+" :: "+number);
        // 通知
        condition.signalAll();
    } finally {
        // 解锁
        lock.unlock();
    }
}
```

## 定制化通信

![image-20260420164518285](C:\Users\Liyal\AppData\Roaming\Typora\typora-user-images\image-20260420164518285.png)

```java
// 第一步 创建资源类
class ShareResource {
    // 定义标志位
    private int flag = 1;  // 1 AA   2 BB   3 CC

    // 创建Lock锁
    private Lock lock = new ReentrantLock();

    // 创建三个condition
    private Condition c1 = lock.newCondition();
    private Condition c2 = lock.newCondition();
    private Condition c3 = lock.newCondition();

    // 打印5次，参数第几轮
    public void print5(int loop) throws InterruptedException {
        // 上锁
        lock.lock();
        try {
            // 判断
            while(flag != 1) {
                // 等待
                c1.await();
            }
            // 干活
            for (int i = 1; i <=5; i++) {
                System.out.println(Thread.currentThread().getName()+" :: "+i+" ：轮数："+loop);
            }
            // 通知
            flag = 2; // 修改标志位 2
            c2.signal(); // 通知BB线程
        } finally {
            // 释放锁
            lock.unlock();
        }
    }
}
```

为什么还要flag 不是都定向通知了线程吗

> 你调用 c2.signal() 时
> 只是把 BB 线程从等待队列里叫醒，让它从 WAITING 状态变成 RUNNABLE（就绪） 状态。
> 但！BB 线程现在还拿不到锁！
> 因为当前 AA 线程还没执行到 unlock()，锁还在 AA 手里！
> BB 线程被唤醒后，必须重新抢锁
> 它会从 await() 方法醒过来，然后立刻再次去抢锁。
> 重点来了：醒来后必须重新检查 flag！()
> 因为在它醒来、到它真正拿到锁开始运行的这段时间里，
> flag 可能已经被其他线程改掉了！也防止虚假唤醒

## 公平锁和非公平锁

**公平锁（Fair Lock）**

先来先排队，不许插队，按顺序拿锁。

- 线程来了就进队列排队
- 锁释放后，**队首第一个线程拿锁**
- 不会有线程长期抢不到锁（无饥饿）
- 缺点：效率低，要维护队列，切换开销大

**非公平锁（Nonfair Lock）**

谁抢到是谁的，允许插队。

- 线程来的时候，直接尝试抢锁
- 抢到就直接执行，不用排队
- 没抢到再去排队

## 可重入锁 (递归锁)

synchronized (隐式锁, 可自动上锁,解锁)
ReentrantLock (显示锁, 手动)

同一个线程，可以重复、多次获取同一把锁，不会自己把自己锁死

# 辅助类

##  CountDownLatch 减少计数（倒计时门闩）

等别人干完，自己再继续

设置一个固定计数器，一个线程干完就`countDown()`减 1，其他线程调用`await()`等待，计数器归 0，等待的线程才全部唤醒继续执行。

一次性工具，倒计时归零后不能重置复用

##  CyclicBarrier 循环栅栏

大家互相等，所有人到齐，再一起出发 

设定一个栅栏人数 N，每个线程到达栅栏位置就停下来等待，凑齐 N 个线程后，所有人同时冲破栅栏继续运行；栅栏用完后可以重置、循环反复使用 

可循环复用，所以叫`Cyclic`（循环）

## Semaphore 信号灯 / 信号量

控制同时运行的线程数量，抢通行证

设置固定数量的 “许可”，线程干活前先`acquire()`拿许可，干完后`release()`归还许可

> 用来限流、控制并发数
>
> 可以实现公平 / 非公平抢许可

## 读锁/共享锁 (死锁)

可以多个线程同时加读锁，一起读数据

但加了读锁，就不能加写锁

## 写锁/排他锁 (死锁)

同一时间只能有一个线程加写锁

写锁和任何锁都互斥（和读锁互斥、和写锁也互斥）

### 锁降级

锁降级 = 先持有写锁 → 在不释放锁的前提下，再加读锁 → 再释放写锁。

最终从 “写锁” 变成 “读锁”，这一过程就叫锁降级

> 现在是**写锁（独占）**，改完数据后，你还想**继续读最新数据**，但不想一直占着写锁不让别人读

意思是保证写完后可以立刻被读，因为写完后可能被其他写锁上锁导致无法读，所以先让读锁上锁防止写锁其他写锁上锁而不能读

# BlockingQueue 阻塞队列

自带阻塞功能的线程安全队列，满了就等、空了就等，专门用来做生产者 - 消费者模型

> 线程安全，内部自带锁 / 阻塞机制
> 往满队列 put 时，线程会阻塞等待，直到有空位
> 从空队列 take 时，线程会阻塞等待，直到有数据
> 天然实现 生产者 - 消费者 解耦

![image-20260420201105708](C:\Users\Liyal\AppData\Roaming\Typora\typora-user-images\image-20260420201105708.png)

##  ArrayBlockingQueue

**数组实现的有界阻塞队列**

- 底层：定长数组，**必须指定容量，容量固定不能变**

- 锁机制：全局一把非公平锁

- 特点：

  - FIFO 先进先出
  - 有界，防止无限堆积内存溢出

  

- 适用：固定大小、流量可控的生产者消费者场景

------

##  DelayQueue

**延迟优先级阻塞队列**

- 特点：**只有到期的元素才能被取出**

- 元素必须实现 `Delayed` 延迟接口

- 无界队列，写入不会阻塞

- 典型场景：

  - 定时任务调度
  - 订单超时自动取消
  - 缓存过期自动清理

  

------

##  LinkedBlockingDeque

**链表实现的双向阻塞队列（Deque）**

- 底层：链表结构

- 特点：

  - 头尾两端都可以插入、取出
  - 既可以做普通队列，也能当栈用
  - 支持有界 / 无界

  

- 额外能力：支持批量操作、可迭代

- 相比 `LinkedBlockingQueue` 功能更强

------

##  LinkedBlockingQueue

**链表实现的无界（可选有界）阻塞队列**

- 底层：链表，默认**近乎无界**（最大容量 Integer 最大值）
- 锁机制：**读写分离两把锁**，并发性能远高于 ArrayBlockingQueue
- 特点：FIFO，吞吐量极高
- 最常见用途：**线程池默认的工作队列**

------

##  PriorityBlockingQueue

**优先级无界阻塞队列**

- 不是 FIFO，**按自定义优先级排序出队**
- 无界队列，扩容增长
- 内部用最小堆实现
- 注意：不会阻塞生产者，只会阻塞消费者（空队列时 take 等待）
- 场景：任务按权重、优先级先后执行

------

##  SynchronousQueue

**同步交接队列（无存储空间）**

- 核心：**本身不存任何元素**
- 生产者 put 之后，必须阻塞，等消费者来 take 配对
- 一对一直接传递，零缓冲
- 分公平 / 非公平模式
- 场景：**一手交钱一手交货，任务直接转交**，Executors.newCachedThreadPool 底层就是用它

| 队列                  | 底层       | 边界       | 核心特点           |
| --------------------- | ---------- | ---------- | ------------------ |
| ArrayBlockingQueue    | 数组       | 有界       | 定长、全局锁       |
| LinkedBlockingQueue   | 链表       | 可选有界   | 读写分离、高并发   |
| LinkedBlockingDeque   | 双向链表   | 可选有界   | 两端操作、双端队列 |
| DelayQueue            | 优先级队列 | 无界       | 延迟到期获取       |
| PriorityBlockingQueue | 最小堆     | 无界       | 按优先级出队       |
| SynchronousQueue      | 无存储     | 真正无容量 | 必须配对交接       |

##  使用方式

`Executors.newFixedThreadPool(int n)` 固定大小线程池

> 线程数量固定，创建时指定核心 / 最大线程数
> 空闲线程不会被回收
> 阻塞队列用 无界 LinkedBlockingQueue
> 任务再多，也只会用固定数量线程慢慢处理

`Executors.newSingleThreadExecutor()` 单线程线程池

> 池子永远只有 1 个工作线程
> 任务串行排队、顺序执行
> 同样用无界队列
> 线程挂掉会自动新建一个补上

`Executors.newCachedThreadPool()` 可缓存弹性线程池

> 线程数量无上限（最大 Integer 最大值）
> 核心线程数 = 0，空闲线程 60 秒就自动销毁回收
> 队列用SynchronousQueue，不存任务，来任务直接新建线程
> 来多少任务，就疯狂创建多少线程

## 原理七参数

可见线程池返回的都是 `ThreadPoolExcutor` 

![image-20260420203512951](C:\Users\Liyal\AppData\Roaming\Typora\typora-user-images\image-20260420203512951.png)

### `corePoolSize`: 核心线程数

永远在线的 “常驻员工”

- 含义：线程池初始化后，默认没有线程。当有任务来时，创建新线程（直到达到核心数）。
- 特性：核心线程默认不回收，哪怕空闲也一直活着。
- 类比：餐厅里的正式厨师，时刻在岗，随时准备做菜。

### `maximumPoolSize`: 最大线程数

最多能雇佣的 “总人数”

- 含义：线程池能创建的线程总数上限。
- 逻辑：当核心线程满了、队列也满了，新来任务会继续创建线程，直到达到这个数。
- 类比：餐厅最大容纳人数。正式厨师（核心）+ 临时工（非核心）总和不能超过这个数。

### `keepAliveTime` : 空闲存活时间

**临时工没事干多久后 “下班”**

- 含义：非核心线程（超出 corePoolSize 的那些线程）空闲多久后被销毁。
- 特性：核心线程默认不受此限制（除非设置`allowCoreThreadTimeOut`）。
- 类比：临时工没事干超过`keepAliveTime`时间，就辞退回家。

### `unit` :  时间单位

**存活时间的计量单位**

- 含义：配合 `keepAliveTime` 使用。
- 常见值：`TimeUnit.SECONDS`（秒）、`TimeUnit.MILLISECONDS`（毫秒）等。

### `workQueue`:  任务队列（阻塞队列）

**任务缓冲区**

- 含义：当核心线程都在忙时，新来的任务放到这个队列里排队等待。

- 核心逻辑：

  1. 核心线程忙 → 进队列
  2. 队列满了 → 启动临时线程
  3. 临时线程也满了 → 触发拒绝策略

  

- 类比：餐厅的候餐区座位。厨师（线程）忙不过来，客人（任务）先在候餐区坐会儿。

### `threadFactory` :  线程工厂

怎么创建线程

- 含义：自定义线程的创建方式。
- 常用用途：给线程起有意义的名字（方便排查日志）、设置守护线程、优先级等。
- 默认：`Executors.defaultThreadFactory()`

### `handler`: 拒绝策略

人满为患、队列爆满时的处理方案

- 含义：当线程数达到`maximumPoolSize`且队列满了，新来任务怎么办。
- JDK 内置 4 种策略：
  1. AbortPolicy（默认）：直接抛异常 `RejectedExecutionException`
  2. CallerRunsPolicy：回退给调用者线程自己执行（降级处理）
  3. DiscardPolicy：默默丢弃任务，不通知
  4. DiscardOldestPolicy：丢弃队列里最老的任务，尝试插入新任务

| 参数                | 核心职责       | 生活类比          |
| ------------------- | -------------- | ----------------- |
| **corePoolSize**    | 常驻员工数     | 正式厨师          |
| **maximumPoolSize** | 总人数上限     | 餐厅总容量        |
| **keepAliveTime**   | 临时工空闲时长 | 临时工闲时辞退    |
| **unit**            | 时间单位       | 换算秒 / 分钟     |
| **workQueue**       | 候餐队列       | 候餐区座位        |
| **threadFactory**   | 招聘方式       | 员工起名、属性    |
| **handler**         | 满员拒绝方案   | 客满不接待 / 排队 |

# Fork / Join 分支合并框架

Fork/Join 它可以将一个大的任务拆分成多个子任务进行并行处理，最后将子任务结果合并成最后的计算结果，并进行输出。Fork/Join 框架要完成两件事情：

Fork：把一个复杂任务进行分拆，大事化小

Join：把分拆任务的结果进行合并

![image-20260420205604822](C:\Users\Liyal\AppData\Roaming\Typora\typora-user-images\image-20260420205604822.png)

## Fork

```
if (任务大小 <= 临界值) {
    // 足够小了，直接执行，不拆了
    return 直接计算结果;
} else {
    // 执行 Fork 动作：拆分成多个子任务
    拆分成子任务A, 子任务B, 子任务C...;
    提交所有子任务去并行执行;
}
```

### RecursiveTask<V>

RecursiveTask<V>：有返回结果的递归任务，继承自ForkJoinTask
专门配合ForkJoinPool线程池使用，用来做「分治 + 并行计算」
对比：
RecursiveTask：有返回值（就是图里这个）
RecursiveAction：无返回值

```java
class Fibonacci extends RecursiveTask<Integer> {
    final int n;
    Fibonacci(int n) { this.n = n; }

    // 核心计算+拆分逻辑
    Integer compute() {
        // 终止条件：任务足够小，不再拆分，直接返回结果
        if (n <= 1)
            return n;

        // 1. Fork拆分：新建子任务f1，计算 F(n-1)，提交异步执行
        Fibonacci f1 = new Fibonacci(n - 1);
        f1.fork(); 

        // 2. 新建第二个子任务f2，计算 F(n-2)
        Fibonacci f2 = new Fibonacci(n - 2);

        // 3. Join合并：
        // f2直接在当前线程同步计算
        // f1.join()：阻塞等待f1异步任务执行完成，拿到结果
        // 最后两个结果相加返回
        return f2.compute() + f1.join();
    }
}
```
